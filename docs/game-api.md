# Методы игры WARLORD (игровой сервер)

Справочник по запросам к игровому серверу. Составлен **по коду** приложения и по **коду самого клиента игры** (`docs/Game.js`, 3,2 МБ, собран Closure Compiler): официальной документации протокола нет. Раздел 4 описывает методы, которые использует приложение, приложение A — все 112 методов клиента. Всё, что не подтверждено кодом, помечено **(?)**.

Читать вместе с кодом:

| Что | Где |
| --- | --- |
| Сборка адреса, серверы, `getGame` | `src/api/game.ts`, `src/api/servers.ts` |
| Сеть: POST/GET, повтор при ограничении частоты | `src/api/http.ts` |
| Разбор ответа (XML/JSON → объект) | `src/api/parse.ts`, `src/api/xml2js.js` |
| Типы ответов | `src/api/gameTypes.ts` |
| Подписи запросов (`fightHash`, `md5`) | `src/profile/bots/hash.ts` |
| Награды: разбор | `src/profile/bots/reward.ts` |
| Служебные профили (чтение чужих данных) | `src/profile/constants.ts` (`DEFAULT_AUTHORIZATION`) |
| **Клиент игры** (все методы, параметры, разбор ответов) | `docs/Game.js` — искать по `send_request(<N>,` или имени функции (`G.raid_goto_pos_start` …) |
| Старое приложение (источник первичных вызовов) | `D:\Repositories\warlord-helper\src\panels\profile\*.js` |

Во всех примерах `getGame(server, body, auth)` — это `body` (параметры метода) и данные авторизации профиля `auth`.

## 1. Транспорт

### 1.1. Серверы

`id` — номер сервера (в профиле `server`), `api` — код в `CONFIG`.

| id | api | Название | Площадка | Хост |
| --- | --- | --- | --- | --- |
| 1 | `vk1` | Эрмун | ВКонтакте | `tmp1-fb.geronimo.su` |
| 2 | `vk2` | Антарес | ВКонтакте | `tmp1-fb.geronimo.su` |
| 3 | `ya` | Эрмун | Яндекс | `gs1.geronimo.su` |
| 4 | `ok1` | Эрмун | Одноклассники | `tmp1-fb.geronimo.su` |
| 5 | `ok2` | Антарес | Одноклассники | `tmp1-fb.geronimo.su` |
| 6 | `gm` | Эрмун | VK Play | `gs1.geronimo.su` |

Постоянные части запроса: `vk*` — `api_type=vk&api_id=5536422`; `ya` — `api_type=ya&api_id=100430`; `ok*` — `api_type=ok`; `gm` — `api_type=gm&api_id=5782`. Путь игры (`config.game`): `warlord_vk/game.php`, `warlord_vk2/game.php`, `warlord_ya1/game.php` (для `ya` и `gm`), `OK_WARLORD/game.php`, `OK_WARLORD2/game.php`. Хаб: `gameHub/index.php` (`gameHubOk/index.php` у OK).

### 1.2. Типы запроса (`type`)

| type | Что | Путь | Параметры |
| --- | --- | --- | --- |
| 1 (по умолчанию) | Игровой метод | `config.game` | базовые + авторизация + `UID` (если тело не пустое) + `body` |
| 2 | Хаб: список серверов игрока | `config.hub` | базовые + `api_uid` + `body` |
| 3 | Без пути и авторизации | — | базовые + `body` (в приложении не используется) |

`body` добавляется **последним** и может перекрыть любой параметр. Порядок параметров в строке запроса важен для тестов (`api.test`), поэтому его не менять.

### 1.3. Авторизация (`GameAuth`: `id`, `login`, `password`)

Обязательны `login` и `password` для type 1 (иначе `buildGameUrl` бросает исключение, а не возвращает `null`).

| Платформа | Параметры игры (type 1) | `UID` (если тело не пустое) | Хаб (type 2) |
| --- | --- | --- | --- |
| vk | `sslt=0&api_uid=<login>&auth_key=<password>` | `id`, иначе `login` | `api_uid=<login>` |
| ya | `sslt=0&api_uid=<login>&lapi_uid=<password>` | `id`, иначе `login` | `api_uid=<login>` |
| gm | `sslt=0&api_uid=<login>&auth_key=<password>&currency=RUB&lang=ru_RU` | `id`, иначе `login` | `api_uid=<login>` |
| ok | `sslt=0&session_key=<password[1]>&api_uid=<login[0]>&auth_sig=<password[0]>&UID=<login[1]>` | `login[1]` | `api_uid=<login[0]>` |

У OK `login` и `password` — составные строки через запятую: `login = "api_uid,uid"`, `password = "auth_sig,session_key"`.

Откуда берутся данные в приложении:
- Игровой профиль пользователя (`botAuth()` в `src/profile/bots/common.ts`): `login = профиль.login || профиль.id || id пользователя ВК`, `password = профиль.auth` (ключ авторизации, который игрок вводит в настройках). Без `auth` открываются настройки.
- Служебные профили `DEFAULT_AUTHORIZATION[server - 1]` — «пустые» аккаунты, через которые читаются **чужие** данные (предметы игрока по его игровому uid, друзья). Лежат в репозитории открыто намеренно.

### 1.4. Отправка

`getData` (`src/api/http.ts`):
- Хост `tmp1-fb.geronimo.su` (VK и OK): **POST** на `origin + pathname`, параметры из query перекладываются в `FormData`; если сервер ответил 500 — повтор **GET** с теми же параметрами. Значения не декодируются, `%2B` и `%3D` заменяются на `+` и `=` до отправки.
- Остальные хосты (`gs1.geronimo.su`): обычный GET.
- Если тело ответа — `Err. More than 1 request per second` или `Too many requests per second.`, ждём 1 секунду и повторяем **без ограничения числа попыток** (так задумано). Таймаутов нет.
- Любая сетевая ошибка или ошибка разбора → `null` (не исключение). Различить «нет ответа» и «пустой ответ» нельзя.
- Очередь запросов (`api/http.ts`): к игровому серверу в пути один запрос, остальные ждут по приоритету (`PRIORITY`: действие игрока, окно, фон), искусственной паузы между запросами нет; после ответа «слишком часто» вся очередь ждёт секунду, зависший запрос освобождает очередь через 15 секунд.
- Параллельность: сервер ограничивает частоту (~1 запрос в секунду на аккаунт). Код друзей (`mapLimit`) идёт максимум в 2 запроса; ограничение обрабатывает `getData` повтором.

### 1.5. Разбор ответа (`parseResponse`)

1. Пробуем `JSON.parse`. Если не вышло — это XML: значения атрибутов перекладываются в двойные кавычки с экранированием (`&`, `<`, `>`, `'`, `"`; `fixXml`), т. к. сервер присылает невалидный XML, затем `x2js`.
2. Если есть корневой узел `data`, возвращается его содержимое.
3. Если разобрать нельзя — возвращается **исходный текст** (строка) либо `null` для пустого ответа. Поэтому ответом может быть и строка с сообщением об ошибке (см. `errorText` в `common.ts`).

Правила получившегося объекта:
- Атрибут XML `name` → поле `_name`, **всегда строка** (числа надо приводить `Number(...)`).
- Дочерние узлы → поля без подчёркивания (`u`, `i`, `r`, `fight` …).
- Один дочерний узел приходит **объектом**, несколько — **массивом** (`asArray()` из `profile/bots/common.ts` выравнивает).
- Хаб (type 2): поле `s` — узлы серверов (`_n` — название, `_uid` — игровой id, `'0'` — персонажа нет). `getGame` для type 2 возвращает узел сервера по названию, а с `completeData` — весь список.

### 1.6. Типичные ответы об ошибках

| Признак | Смысл |
| --- | --- |
| Корневое поле `msg` (строка) | Сообщение игры: «Недостаточно ресурсов.», «Необходимо состоять в Гильдии.», «Ваша гильдия не имеет захваченных территорий.», «Вы уже забрали свою долю на сегодня.», «На сегодня хватит! Можно продолжить завтра.» |
| Поле `err_msg` | Ошибка авторизации/запроса (читается в `errorText`) |
| В ответе нет ожидаемого узла (`u`, `fight`, `r` …) | Метод не выполнился (нет награды, лимит, не хватает ресурса); вызывающий код трактует отсутствие узла как отказ |

Ошибок по HTTP-коду, кроме 500 на tmp1-fb, не различается.

### 1.7. Как шлёт запросы сам клиент (`docs/Game.js`)

Клиент (`C.send_request`) отправляет **POST** `application/x-www-form-urlencoded`: строка авторизации + `&UID=<id игрока>&_l=<язык>&sslt=<соль сессии>` + параметры метода + `&i=<N>`, а также `d` (метка времени и «1»), `pf` (тип устройства), `cv=1.2`. Приложение `d`, `pf`, `cv`, `_l` не шлёт, и сервер отвечает.

Любой ответ может содержать общие узлы (`G.get_answer`), приложение их не читает:

| Узел | Смысл |
| --- | --- |
| `msg` | Текст, который клиент показывает игроку |
| `quest` (`t`, `v`, `c`) | Прогресс заданий |
| `add_ach` (`id`, `val`) | Очки достижений |
| `subs` (`v`) | Статус подписки |
| `err` (`v`) | Код ошибки (клиент показывает «m13» + код) |
| `one_wnd` | Игра открыта в другом окне (ошибка) |
| `maintenance` (`ttl`) | Через сколько секунд сервер перезагрузится |

Подписи `g_sig` у части методов — MD5 (`Oc.encode` в клиенте, нижний регистр) от строки параметров и «соли» метода. Известные: `24` — `region_id + "ja6"`; `49` — `clan_id + "hsK18"`; `46`/`95` — `id + "bska"`; `52` — `clan_id + id + "d54z"`; `54` — `clan_id + id + "vzdwff"`; `55` — `id + "fhJa"`; `56` — `id + "dS4w"`; `58` — `t + "xmdwj"`; `44` — `r + t + t1`; `45` — `r + userId + t + t1 + "Hfdr1"`.

**Правило для приложения** (со слов владельца): сервер сверяет подпись не везде, где-то она только для вида; где именно, видно лишь на практике. В приложении подпись ставится там, где она реально нужна (сейчас это `24`; `49` работает без неё). **Для методов, которых в приложении ещё нет, подпись по умолчанию ставить**, соль брать из этой таблицы или из функции клиента (`Oc.encode(...)` рядом с `send_request`), и отказываться от неё только после проверки на практике.

### 1.8. Особенности сервера (со слов владельца)

Многие проверки на сервере упрощены; это даёт возможности в обход обычного хода игры. Что известно:
- **Дружба не проверяется.** Там, где игра ожидает id друзей, можно передать id любого игрока, сервер не сверяет, что он действительно друг. Например, в `i: 7` (`f_data`) и `i: 67` (`sdata`) можно запросить сообщения КПК любого игрока и получить приглашение на босса, создатель которого в друзьях не состоит. Так же устроено `i: 8` (приложение перебирает ключи 1…15, а не id друзей). По клиенту id друзей принимают и другие методы (`i: 29`, `i: 53`, `i: 86`, `i: 87`, `i: 99`, `i: 103`); **(?)** действует ли у каждого то же самое, проверять на практике.
- **Подписи `g_sig`** проверяются не везде (см. 1.7).
- **Удача `m0`** в бою у всех равна 3 (см. 4.3).

При добавлении нового метода не полагаться на то, что клиент делает проверки: сервер их часто не повторяет, и наоборот, из «обычного» клиентского поведения нельзя выводить ограничения сервера.

## 2. Общие форматы

### 2.1. Игрок (`u`) — `GameUser`

Атрибуты узла `u`, все строки. Поля, которые читает приложение:

| Поле | Смысл |
| --- | --- |
| `_id` | Игровой id игрока (отличается от id ВК); нужен как `UID` и в запросах с телом |
| `_vkId`, `_okId`, `_fbId`, `_gmId`, `_mmId`, `_kgId`, `_exId`, `_rbId` | Внешние id по площадкам (вне ВК приложение их не использует) |
| `_name` | Имя (может быть пустым → «Player<id>») |
| `_lvl`, `_exp` | Уровень, опыт |
| `_dmgi` | Атака (с предметами) |
| `_end`, `_endi` | Выносливость и от предметов; **здоровье = (`_end` + `_endi`) × 15** |
| `_hp`, `_mhp` | Текущее/максимальное здоровье (в боях читаются из `fight`) |
| `_en` | Энергия |
| `_m1` серебро, `_m2` рубины, `_m3` золото, `_m4` аметисты, `_m5` топазы, `_m6` турмалины, `_m7` пергаменты, `_m9` редкие жемчужины | Ресурсы |
| `_pf1` | Еда питомца |
| `_item1` молнии, `_item2` целебные зелья, `_item3` огня | Расходники (в наградах те же поля называются `_i1`, `_i2`, `_i3`) |
| `_s1`…`_s4` | Уровни навыков: `_s3` невидимый удар (рейды, арена), `_s4` мастер целитель |
| `_ap` | Кубки арены |
| `_al` | Лига арены (1–9, 0 — нет) |
| `_pet` | Id активного питомца (`0` — нет) |
| `_clan_id` | Id гильдии (`0` — нет) |
| `_va` | Премиум (`0` — нет) |
| `_lott` | Секунд до бесплатной лотереи |
| `_bd` | Секунд с регистрации; `_l_t` — секунд с последнего входа |
| `_a1`…`_a3`, `_aid` | Слои внешнего вида персонажа и аватар |

Полный набор полей «пустого» игрока — `GAME_FIELDS` в `profile/constants.ts` (`emptyGameUser()` заполняет их нулями, когда данных нет).

### 2.2. Награда — `Reward`

В ответе награда — **один или несколько узлов `r`** (клиент `XML_to_CRewardData` обходит все `r` и суммирует). Приложение собирает их `normalize`/`joinRewards`. Поля одного узла (все строки с числом, `0` и отсутствие поля равнозначны):

| Поле | Ресурс | Поле | Ресурс |
| --- | --- | --- | --- |
| `_m1` | Серебро | `_i1` | Свитки молнии |
| `_m2` | Рубины | `_i2` | Целебные зелья |
| `_m3` | Золото | `_i3` | Свитки огня |
| `_m4` | Аметисты | `_i4`, `_i5` | Другие расходники **(?)** |
| `_m5` | Топазы | `_pf1` | Еда питомца |
| `_m6` | Турмалины | `_en` | Энергия |
| `_m7` | Пергаменты | `_exp` | Опыт |
| `_m8` | **(?)** | `_ap` | Кубки арены |
| `_m9` | Редкие жемчужины | `_k1`…`_k10` | Ключи (к фонам) |
| `_event1`…`_event12` | Очки событий | `_bscore` | Очки босса **(?)** |
| `_chm1`…`_chm5` | Шансы выпадения (для показа, не награда) | | |

Логи приложения (`reward.ts`) показывают только `_m1…_m7`, `_m9`, `_i1…_i3`, `_pf1`, `_en`, `_exp`; остальные поля (`_ap`, `_k*`, `_event*`, `_bscore`, `_i4`, `_i5`, `_m8`) приложение игнорирует.

Предмет в награде — одно из двух:
- атрибуты самого узла `r`: `_item` (id, `0` — нет) и `_type`; либо
- дочерние узлы `i` с `_id`, `_type`.

Дополнительно у предмета бывают `_cnt` (количество), `_b` (куплен), `_v1`…`_v3` (параметры, например уровень). Приложение учитывает `_id`/`_item` и `_type`.

| `_type` | Что | Где искать название |
| --- | --- | --- |
| `1` | Фон (комната) | — («Новый фон») |
| `6` | Фрагмент коллекции | предмет или ресурс, в `fragments` которого есть `_id` |
| `8` | Заточка | предмет `_id` |
| `11` | Камень инкрустации | `data/stones.json` |
| иное | Предмет | `data/items.json` по `id` |

Нюансы (`reward.ts`):
- Если `normalize` получил массив узлов: узлы с `_type` — предметы (их `_item` становится `_id`), остальные сливаются в один.
- Несколько наград складываются `joinRewards` (ресурсы суммой, предметы списком).
- Игровой id предмета (`Item.id`) не равен индексу в каталоге: в данных разделов `ItemRef.id` — **индекс**, у владельца — **игровой id**.
- Узел `rstep` (шаг рейда) тоже содержит награду в своём `r`: так сервер возвращает награду за действие в рейде отдельно от накопленной награды рейда (`uraid.r`).

### 2.3. Профиль (`getStats`) — запрос без `i`

Запрос `getGame(server, {}, auth)` (пустое тело, авторизация игрока). Возвращает:

| Узел | Содержимое | Использует |
| --- | --- | --- |
| `u` | Игрок (2.1) | все боты |
| `i` | Предметы игрока (`ProfileResponse.i`): `_id` игровой id, `_o`=`1` — предмет есть, `_u` уровень улучшения, `_st11`,`_st12`…`_st32` камни (раздел, уровень), `_st_dmg`,`_st_en`,`_st_end` бонусы камней | кузница, инкрустация |
| `iupgrade.i` | Заточки: `_id` предмета, `_cnt` количество | кузница |
| `j` | Здания на карте: `_r`,`_rn` (район, здание), `_t` секунд до обыска (`<= 0` — готово), `_id`, `_lvl` | ресурсы (обыск, улучшение) |
| `chests.ch` | Сундуки: `_id`, `_ci` тип (индекс `CHEST_NAMES`), `_o` (1 — взлом запущен: ждёт или готов к сбору; 0 — закрыт), `_ot` секунд до открытия | ресурсы |
| `mypets.p` | Питомцы игрока: `_is_loot`=`1` — ушёл на поиск, `_end_time` секунд до возвращения | ресурсы |
| `pets.p` | Справочник питомцев: `_id`, `_lp` нужно еды | ресурсы |
| `uraid` | Текущий рейд (см. 4.2) | рейды |
| `raids_cnt._v` | Сколько рейдов уже запущено сегодня (лимит 3) | рейды |

Пустой ответ (`!data.u`) означает неверный пароль/ключ; боты открывают окно настроек и возвращаются на страницу профиля (`loadBotProfile`).

## 4. Методы подробно

Соглашения: «Ответ» — только поля, которые читает код; «Отказ» — как код распознаёт, что действие не выполнено. Все значения атрибутов — строки.

### 4.1. Профиль, хаб, чужие данные

#### Хаб (type 2) — `getGame(server, {}, { login, password }, 2)`
- Параметры: `api_uid=<login>`.
- Ответ: узел сервера (по названию из `findServer`): `_uid` — игровой id персонажа (`'0'` — нет), `_n` — название.
- С `completeData=true` возвращает список всех серверов логина (`_uid`, `_n`). «Проверить» в настройках логина показывает серверы, где `_uid != 0`.
- Использование: перед чтением чужих данных (`i: 39`), чтобы узнать `uid`.
- Для хаба логин/пароль берутся `профиль.login || профиль.id || пользователь ВК` (при отсутствии `auth` — id пользователя).

#### `i: 39` — предметы и данные игрока по uid
- Параметры: `t` = `_uid` из хаба. Авторизация — **служебный профиль** сервера (`DEFAULT_AUTHORIZATION[server - 1]`).
- Ответ: `u` (игрок), `i` (предметы: `_id`, `_o`=`1` — есть у игрока, `_u`, камни).
- Отказ: нет `u` → персонаж не найден (`found: true, game: пустой`).
- Использование: магазин/коллекции/инкрустация профиля, анализ сезонов/ивентов (`_bd` / 86400 = дней в игре).

#### `i: 7` — персонажи друзей (`G.FriendsGetData` в клиенте)
Назначение: по списку внутриигровых идентификаторов друзей (для ВК — id ВКонтакте) получить профили **тех из них, кто играет** (остальные в ответ не попадают). Клиент использует это, чтобы показать друзей в игре; приложение — для рейтинга друзей по урону, здоровью, уровню и последнему входу.
- Запрос: POST `i=7`, `f_data` = `<data><u>id</u><u>id</u>…</data>`, где `id` — идентификатор друга на площадке игрока (у ВК — `vkId`; клиент берёт поле `<площадка>_id`), и `t` = **номер порции** (с 1). Клиент режет список на порции по **400** друзей и шлёт их по очереди; приложение — по 300 и без `t` (сервер отвечает без него). Служебный профиль сервера.
- Ответ: `u` — игрок или массив игроков. Поля: `_id`, `_vkId`/`_okId`/`_fbId`/`_kgId`/`_mobId`/`_mmId`/`_exId`/`_gmId`/`_rbId` (внешние id), `_aid` аватар, `_name`, `_lvl`, `_exp`, `_a1`…`_a5` внешность, `_room` фон, `_d2`…`_d11` надетые предметы (игровые id), `_l_t` секунд с последнего входа, `_loot` (обыскан ли сегодня), `_clan_id`, `_clan_r` ранг в гильдии, `_dmgi`, `_end`, `_endi`. Приложение читает `_vkId`, `_id`, `_name`, `_dmgi`, `_end`, `_endi`, `_lvl`, `_exp`, `_bd`, `_l_t`. Дополнительно сервер присылает узлы `ur` — см. ниже; приложение их не использует.
- Отказ: нет `u` → страница считается неудачной, весь запрос — ошибка (`scanFriends` не возвращает частичный список).
- Список друзей ВК берётся отдельно (`friends.get`, до 5000), для каждого порция уходит одним запросом.

Живой ответ `i: 67` присылает поля **дочерними элементами**, не атрибутами: `<ur><id>36294</id><uid>171482060</uid><t>1</t><v1>559</v1><v2>69</v2><v3>341584526</v3><v5>0</v5><d1>1</d1><n>Byakuya</n></ur>`; пустой ответ — `<data></data>`. Приложение (`profile/invites/`) читает оба варианта.

**Узлы `ur` — сообщения КПК (PDA): друзья зовут на помощь в бою.** Клиент передаёт их окну КПК (`pda_wnd.load_messages`), оно показывает карточку «друг зовёт в бой» с иконкой NPC, именем друга и кнопками «принять» и «отклонить». Поля:

| Поле | Смысл |
| --- | --- |
| `id` | Номер сообщения |
| `uid` | Игровой id друга, который позвал |
| `t` | Тип сообщения; `1` — приглашение в бой (другие типы клиент не обрабатывает) |
| `v2` | Id NPC (босса); по нему берётся иконка `npc/icons/<v2>.png` и данные NPC |
| `v3` | Id боя (`fight_id`); при принятии уходит как `fid` в запросе боя |
| `v5` | Id гильдии: `0` — зовут всех, иначе видно только участникам этой гильдии |
| `d1` | Счётчик убийств/участия; для NPC с лимитом показывается как `d1 / 300` |
| `n` | Имя отправителя (если задано, показывается вместо имени игрока) |
| `v1` | Клиент не использует; предположение владельца — внутренний признак версии метода на сервере **(?)** |

**Уровень получателя** (со слов владельца): сервер отдаёт приглашения на боссов только в пределах того, что доступно по уровню запрашивающего аккаунта. Служебный профиль (1 уровень) большинство приглашений не получит, поэтому сводку приглашений нужно запрашивать **аккаунтом самого пользователя** (с ключом авторизации, как боты); у каждого аккаунта свой лимит «не чаще раза в секунду».

Клиент показывает приглашение только если: `t` = 1; босс не отключён в фильтре КПК; `d1` < 300 (или у NPC нет лимита); регион NPC открыт игроку; `v5` равен 0 или гильдии игрока. «Принять» открывает бой с этим NPC и `interfere = uid` (помощь другу). **Проверено на практике** (22.10.2026, аккаунт владельца, Эрмун ВК): запрос `i: 67` с `sdata` из 300 игровых id, `t=33`, `d=<время>` принимается; пустой ответ — `<?xml version="1.0" encoding="utf-8"?><data></data>` (парсер возвращает сырую строку, а не объект). Живых приглашений на момент проверки не было, поэтому формат самих `ur` (дочерние элементы `<id>…</id>` как в клиенте или атрибуты) не подтверждён; приложение читает оба. Три порции по 300 (704 игрока) отвечают примерно за 0,4 с, ограничение «раз в секунду» не сработало.

Само приглашение друг создаёт методом `i: 29` (`call_friends_infight`, `t` — фильтр). Те же узлы `ur` возвращает `i: 67` (`get_pagerdata`: `sdata` = `<data><u>id</u>…</data>` по 400 id, до 15 порций, `t=33`) — «пейджер» по произвольному списку игроков.

#### `i: 49` — гильдия
- Параметры: `t1` = `_clan_id` игрока.
- Ответ: узел `clan`: `bldngs.b` (здания гильдии; у `_id`=`5` поле `_ptl` — секунд до сбора), `hist.h` (история событий: `_t` тип 18 или 20 — набег, `_v3`=`1` — выигран, `_v2` id набега, `_v1` id врага, `_d` дата).
- Отказ: `clan` отсутствует → профиль считается неисправным (пароль).

### 4.2. Рейды

Карта рейда — граф точек (`profile/bots/raidMaps.ts`, `RAID_MAPS[рейд - 1]`); путь между точками считает `raidPath()` алгоритмом Дейкстры. Рейды: 1 «Подземелье форта», 2 «Подвал часовни», 3 «Паучий лес»; режимы 0–3 (лёгкий … легендарный). В день запускается не более 3 рейдов (`raids_cnt._v`).

#### Состояние рейда — `uraid` (в ответе профиля и `i: 76`)

| Поле | Смысл |
| --- | --- |
| `_id`, `_mode`, `_atk`, `_hp` | Рейд, режим, атака/здоровье игрока в рейде |
| `_pos` | Текущая точка (`0` — не начат) |
| `_tleft` | Секунд до конца рейда |
| `rc` | Сундуки: `_p` точка, `_t` тип 1–5, `_p1` цена в энергии, `_p2` цена в рубинах, `_s` статус |
| `bp` | Бочки: `_p` точка, `_s` статус |
| `rb` | Боссы: `_id`, `_p` точка, `_s` статус (тип босса по `_id`: `bossType()` в `raidData.ts`) |
| `r` | Накопленная награда рейда (`Reward`) |
| `vp` | Посещённые точки (`_p`) |
| `am` | Переход в процессе: `_t` когда закончится, `_p` в какую точку |

Статусы сундука (клиент `CRaidsChest`): `1` — закрыт, можно открыть; `2` — уже открыт; `3` — сломан (в обоих случаях открыть нельзя). У бочки `1` — можно открыть. У босса `0` — жив, `1` — убит. Приложение после открытия само выставляет `status = 0`. Энергия на открытие по таблице приложения: бочка 3; сундук `[0, 8, 14, 17, 18, режим 2 ? 25 : 20][тип]` (сервер присылает точную цену в `_p1`, приложение берёт из таблицы); завершение рейда — 5; бой: главный босс 6, обычный 3 (в итоговой энергии учитывается 1).

#### `i: 76` — создать рейд
- Параметры: `t` = номер рейда (1–3), `t1` = режим (0–3). Ответ: `uraid`, отказ — нет `uraid`. Вызывается, если активного рейда нет и использовано меньше 3 попыток.

#### `i: 77` + `i: 81` — переход между точками (два шага)
Клиент делает переход в **два запроса**: `77` начинает, `81` завершает.
1. `i: 77`, `t` = номер точки (соседней). Ответ `res`: `_v` = `1` — переход начат, `_d` — **задержка перехода в секундах** (в игре 5 с; сервер хранит это как `uraid.am`).
2. Игра ждёт `_d` секунд и вызывает `i: 81` (без параметров). Ответ `res`: `_v` = `1`, `_p` — новая позиция; плюс награда за шаг (`r` и `rstep.r`).

Приложение вызывает `81` **сразу**, не дожидаясь задержки; сервер это принимает (проверено практикой, по коду клиента проверка не видна). Это основной выигрыш в скорости бота.

#### `i: 79` — открыть сундук в текущей точке
- Параметры: `t1` = **способ оплаты**: `1` — энергия (`_p1`), `2` — рубины (`_p2`). Приложение всегда шлёт `1`. Перед вызовом приложение отдельным запросом проверяет энергию (`_en` ≥ цена).
- Ответ: `rstep.r` — награда за шаг, `raid_chest` с `_s` — новый статус сундука. Нет `rstep.r` — «Нет награды».

#### `i: 82` — открыть бочку в текущей точке
- Без параметров. Стоит 3 энергии. Ответ: `rstep.r`.

#### `i: 80` — завершить рейд
- Без параметров. Ответ `res._v` = `1` — завершён, в ответе награда (`r`), иначе возможен `msg`. Стоит 5 энергии (проверяется заранее).

#### Бой с боссом рейда — `i: 11` + `i: 12`
1. `i: 11`: `t` = id босса, `t2` = **тип боя** (`3` — рейд), `t3` = бой с другом (`0`), `t4` = вмешательство (`0`), `t5` = бой гильдии (`0`); клиент ещё шлёт `fid` (id боя, для рейдов не нужен). Ответ: `fight` с `_hp` (здоровье босса), `_dmg` (его атака), `_myhp`, `_mhp`; при ошибке возможен `a._val`. Если `fight` нет — приложение повторяет через 3 секунды, затем отказ.
2. Бой рассчитывается **на клиенте** (`simulateBossFight`): навык каждые 9 очков, свитки молнии/огня, обычный удар.
3. `i: 12`: `t` = `fightHash(fightKey({...}))` (раздел 5). Успех — `fight._hp` ≤ 0; ответ включает `_mhp`, `_dmg` для лога.
4. Если расчёт показывает, что босса не убить, бот останавливается и через 3 секунды повторно отправляет тот же `i: 11` **(?)** (предположительно, чтобы сбросить созданный бой; ответ не читается).

### 4.2а. Кооперативный бой с боссом по приглашению (проверено на живом сервере)

Бой общий: здоровье босса снижают все игроки, у каждого свой вклад (`l`: `id`, `n`, `ava`, `dd`). Параметры боссов лежат в профиле: узел `npcs.npc[].u` — `_id`, `_rid`/`_rn` (регион и место), `_type` (`1` — общий бой), `_rq1` (нужный уровень), **`_rq2` — стоимость входа в энергии** (в клиенте `req_en`), `_rlmt` (попыток в сутки), `_rtm` (секунд на восстановление попытки), **`_epr` — цена побега** (в клиенте `escape_price`, не энергия), `_mod_hp`, `_dmg`; `r` — награда.

**Текущий бой** игрока приходит в профиле (`getStats`): узел `fight` с атрибутами боя (`fid`, `eid`, `hp`, `mhp`, `dmg`, `myhp`, `myr`, `time` — секунд **с начала** боя, `res`: `2` идёт) и дочерними `u` (босс) и `l` (участники). Если боя нет — `<fight eid="0"/>`.

1. `i: 10` — данные боя, **ничего не меняет**: `t1`=`rid`, `t2`=`rn`, `t3`=`uid` приглашающего, `t4`=id босса, `t5`=`type`, `fid`=`v3` из `ur`. Ответ: `fight` (`id`, `clan`), `ltop` (топ убийц), `my_rating`, `u` — босс (`hp`/`mhp`, `avail` — попыток осталось, `nrgn` — **секунд до новой попытки**), `r` — награда. **Если бой уже закончился, `fight id` в ответе — другой (новый, с полным здоровьем босса)**: так узнаётся, что приглашение устарело. Входить по такому приглашению нельзя: сервер создаст новый бой и спишет попытку.
2. `i: 11` — вход в бой (списывает энергию `rq2` и попытку): `t`=id босса, `t2`=`type`, `t3`=`0`, `t4`=`uid`, `t5`=`0`, `fid`. Ответ: `fight` (`hp`, `mhp`, `dmg`, `myhp`, `myr`, `time`, `res`) с дочерними `u` и `l`.
3. `i: 12` — удары, `t` = `fightHash(fightKey({...}))`. **Сервер принимает любое число ударов в одном запросе**, но проверяет расчёт: при несходящихся `dd`/`dg`/`r` отвечает `<err v='1011'/>` (или `102`). Урон считается так (все раунды дают +1 ярости, ярость на сервере не ограничена внутри запроса и обрезается до 10 после него; старт боя — 10):
   - раунд: при выбранном навыке и хватающей ярости сначала удар навыком, затем обычный (рукой, свитком молнии `c1` = ×1,5 или свитком огня `c3` = ×3); `s0` — только ударов рукой; `r` = раундов + ударов навыком;
   - навыки: `s1` Свирепый удар — стоит 3 ярости, урон +5 за уровень, босс отвечает; `s2` Блок щитом — 4 ярости, урона навыка нет, ответ босса на этот удар снижается на уровень навыка; `s3` Невидимый удар — 9 ярости, +7 за уровень, босс на него не отвечает;
   - `dd` — нанесено, `dg` — получено (ответ босса `dmg` после каждого удара, кроме удара `s3`); `c2` — зелья лечения (`item2` в профиле), каждое лечит 250 + 3 за уровень навыка 4 (`s4`) и учитывается отдельно от `dg`; `item1`/`item3` — свитки молнии и огня.
   - **Пустой раунд** (все поля нули) возвращает текущее состояние боя: так клиент и приложение обновляют бой, пока игрок не бьёт.
   Ответ: `fight` (`hp`, `myhp`, `myr` — ярость, `res`: `2` идёт, `3` босс побеждён), `l` (участники и урон), `a` (`res`, `dd`, `rid`). **Когда босса побеждён, награда приходит в ответе на любой раунд**, в том числе пустой, всем участникам: узел `r` (`exp`, `m3`), а убийце ещё и узел-предмет (`item`, `cnt`, `type`); `npc.u` в таком ответе содержит `hp` ≤ 0, `avail`, `nrgn`. После этого `fight` в профиле снова `eid="0"`.

**Свой бой без приглашения:** `i: 11` с `t`=id босса, `t2`=`type`, `t3`=`0`, `t4`=`0`, `t5`=`0`, `fid`=`0` создаёт новый бой (проверено); `i: 10` с `fid`=`0` присылает только `u` босса с `avail` и `nrgn` (попытки). Боссы, с которыми так можно начать бой, — с `_type` = 1 (общие и одиночные). **Позвать друзей:** `i: 29` без `t` (так клиент делает «Позвать всех»), ответ `a res="1"`; вживую не проверялся, чтобы не рассылать приглашения реальным игрокам. **Погибший персонаж остаётся в бою** (снято на живом боссе): профиль по-прежнему содержит узел `fight` с `myhp="0"`, `res="2"` и теми же `fid`/`eid`, а пустой раунд `i: 12` (ключ приложения: `s0=0, s4=1, r=0`, `dd=0`, `dg=0`) возвращает обычный `fight` с `myhp="0"`, журнал `l` с уроном персонажа и `a res='2'`. **Удары после гибели сервер отклоняет: `<err v='1012'/>`** (проверено кнопками Max и Kill на погибшем персонаже), поэтому приложение блокирует все кнопки ударов, пока `myhp` ≤ 0; урон, который набрал персонаж к гибели, остаётся засчитанным. Внутри одного запроса удары, после которых персонаж погибает, принимаются (последний удар может убить). Приложение считает бой проигранным, когда `myhp` ≤ 0, а босс жив; бой общий и идёт дальше. Узел `fight` в ответах пишется с табуляциями и переводами строк внутри тега (`<fight\n noreward = "0" …`): разбирать его регулярным выражением нельзя, только XML-парсером.

**Время боя — всегда 2 часа** (со слов владельца): `fight.time` в ответах — секунды с начала боя, когда он доходит до 7200, босс побеждает, награды нет. **Убийства боссов** игрока лежат в профиле: `npcs.kill` (`id` босса, `v` — сколько раз убит, `fine` — штраф за побег). Район открывается, когда хватает его уровня (`lvl`) и убит босс, который он требует (`boss` — индекс в справочнике боссов).

**Слабая проверка боя на сервере (наблюдение).** Сервер сверяет только арифметику пакета: сходятся ли `dd`, `dg`, `r` и число применённых навыков с формулами выше. Он не проверяет последовательность раундов: здоровье персонажа в пакете уменьшается на `dg` в конце, а победа над боссом, судя по всему, проверяется раньше гибели, поэтому один пакет `max` убивает босса даже тогда, когда по расчёту персонаж погиб бы раньше (так работает кнопка Max в приложении, поведение оставлено намеренно). Лимита ударов в одном запросе нет.

Приложение (`profile/invites/`): `accept.ts` — проверка и вход в бой, создание боя, позвать друзей; `battle.ts` — расчёт ударов (в т. ч. `survivableRounds` для Max), подбор настроек для убийства, метка SOLO; `battleStore.ts` — контекст страницы (персонаж, убийства, «текущий бой» из профиля), бой открытого окна (живёт, пока открыто окно боя или участников, потом убирается; в хранилище боёв после закрытия ничего не остаётся), раунды по очереди, `showBattle`/`openCurrentBattle`; `battleFlow.ts` — конец боя и обновление; `poller.ts` — опрос раз в минуту: свежий профиль (бой, в котором персонаж) и приглашения; `attempts.ts` — попытки на боссов по видимым строкам; `bossList.ts` — выбор боссов (локации, причины блокировки); `settings.ts` — навык и расходники в VK Storage по профилю и боссу; `killAccess.ts` — белый список кнопки Kill (`execute.getProfileBossesWhitelist`, по `vk_user_id` запустившего). Окна боя, итогов, участников, приглашения и создания — в `modals/profile/`.

**Какие районы открыты (по коду клиента, `docs/Game.js`, не проверено запросом).** В профиле `u` атрибут `locm` — число открытых районов (`region_id_max` клиента); при смене региона клиент ставит `region_id_max = max(region_id + 1, region_id_max)`. Босс доступен для боя, если номер его района (`_rid` в `npcs`) меньше `locm`, тип боя 1 и `is_solo` (`solo` в узле NPC) равен 0. Приложение проверяет `_rid < locm` (и уровень босса `_rq1`), у `_solo` фильтра пока нет.

**Проход «Убить всех»** (`modals/profile/KillAllModal.tsx`, `profile/invites/killAll.ts`): по избранным боссам. Одно убийство: `i: 11` без `fid` (`createFightUnchecked`, проверки персонажа сделаны перед проходом) и один запрос `i: 12` с рассчитанными ударами (обычные удары и «Невидимый удар», без свитков и зелий), победа приходит с наградой в `r`. После убийства обновляются профиль и попытки этого босса. Метка SOLO и фильтр прохода считают то же самое: только обычные удары и «Невидимый удар».

### 4.3. Арена

#### `i: 9` — противник
- Клиент (`get_fight_data`): `t: 1` — найти противника на арене; `t: 0` + `t1: <id>` — данные конкретного игрока; для боёв региона, NPC и боссов используется `i: 10` с `t1…t5` и `fid`.
- Ответ: `u` — противник (`_id`, `_name`, `_aid` аватар, `_end`, `_endi`, `_dmgi`, `_s1`, `_s2`, `_s3`), `my_rating` (`_val` — место игрока в лиге), `norew` (`_val` — награды за этого противника нет), `ltop` (топ лиги: `u` с `_id`, `_n`, `_p` кубки, `_lvl`, `_num`, `_ava`), `clan`, `fight` (`_clan`). Приложение читает `u` и `my_rating`.
- Отказ: нет `my_rating`. При загрузке страницы тот же вызов даёт `rating`; перед каждым боем вызывается снова.

#### `i: 121` — пропустить противника
- Без параметров. Ответ `res._v` = `1` — пропущен (приложение ответ не читает). Стоит 4 энергии (приложение само уменьшает локальный счётчик).

#### `i: 11` — начать бой с противником
- Параметры: `t` = `enemy._id`; приложение не шлёт `t2…t5` (клиент: `t2` — тип боя, `0` для арены). Ответ: `fight`; при отсутствии повтор через 3 секунды. Стоимость боя в золоте: `FIGHT_PRICE[лига]` = `[0, 10, 30, 50, 90, 150, 250, 350, 500, 650]`.

#### `i: 12` — раунд боя
- Параметры: `t` = `fightHash(fightKey({...}))`. В клиенте `getSyncRequestData`: атрибуты `d`: `s0…s4` — сколько раз применён каждый навык (`skill_4` клиент всегда ставит `1`), `c1…c5` — использованные расходники, `m0` — **удача игрока** (`user_data.luck`; приложение шлёт `3`: по словам владельца, удачи в игре нет и у всех она 3, это наследие каркаса прежней игры от тех же разработчиков), `r` — номер раунда, `dd` — нанесено урона, `dg` — получено.
- Ответ: `a` (`_res`, `_dd`, `_rid`), `fight` (`_hp` противника, `_myhp`, `_myr` — очки ярости игрока, `_esk` — навык, применённый противником), журнал боя `l`, награда `r`, `rstep.r`, `npc.u`. Победа — `_myhp > 0` и `_hp ≤ 0` (+19 кубков), поражение — `_myhp ≤ 0` (−16). Награда при выпадении сундука приходит массивом. Раундов может быть много; код ограничивает цикл (`maxRounds`).
- **Гибель персонажа закрывает бой.** В отличие от боссов (раздел 4.2а), арена не принимает удары после `_myhp ≤ 0`: проверено на сильном противнике, раунд после гибели вернул `a` с пустыми `_res`, `_dd`, `_rid` и без `fight`. Поэтому «драться с сильными» невозможно: сильных противников остаётся пропускать (`i: 121`) или проигрывать.
- Ключ боя (`fightKey`, арена): базовые значения `s0=1, s1=0, s2=0, s3=0, s4=0, c1…c5=0, m0=3 (удача), r=1, dd=0, dg=0`. Варианты по навыку противника (`_esk`): 1 — `dd=мояАтака, dg=атака+_s1*5`; 2 — `dd=мояАтака-_s2, dg=атака`; 3 — `dd=0, dg=атака+_s3*7`; иначе `dd=мояАтака, dg=атака`. Если очки ярости `_myr ≥ 9` и есть `_s3`: `s0=0, s3=1, dd=мояАтака+_s3*7, dg=0`.

## 5. Подписи

- **`fightHash(key)`** (`hash.ts`): `base64(utf8(key)) + "Bd" + случайная цифра 1–9 + "rP"`, строка разворачивается задом наперёд и снова кодируется в base64. Результат — значение `t` в `i: 12`. Ключ боя — XML-фрагмент `<data><d s0=".." s1=".." … dd=".." dg=".." /></data>` (`fightKey` в `ArenaBotPanel.tsx` и `raidData.ts`). Поля рейдов: `s0`=ударов рукой, `s3`=ударов навыком, `c1`=молнией, `c3`=огнём, `r`=ударов+навыков, `dd`=нанесено, `dg`=получено; базовые значения рейда `s4=1, m0=3, r=0`.
- **`g_sig`** улучшения здания (`i: 24`): `md5(_r + "ja6")` (`md5` в `hash.ts`).
- Остальные методы подписей не требуют.

## 7. Как добавить новый метод

1. Найти вызов в старом приложении (`src/panels/…`) и убедиться, что параметры/ответ те же; выяснить, нужен ли служебный профиль.
2. Вызывать через `getGame(bot.server, { i: N, … }, bot.auth)`; для чтения чужих данных — `DEFAULT_AUTHORIZATION[server - 1]`.
3. Описать читаемые поля ответа в `src/api/gameTypes.ts` (атрибуты — `Attrs`, один/несколько узлов — `OneOrMany`).
4. Обрабатывать отказ: ответ может быть `null`, строкой, без нужного узла или с `msg`; всегда проверять нужный узел (`data?.r`), а не только факт ответа.
5. Действия бота: учесть остановку (`flags.start`, `useBotRunner`), не бросать начатое (например, начатый бой доводить до конца).
6. Награды разбирать `parseReward` / `joinRewards`.
   Подпись `g_sig`: для нового метода ставить по умолчанию (соль — в разделе 1.7 или в функции клиента), убирать только после проверки на практике.
7. Добавить тест с подставным `getGame` (образец — `resourcesActions.test.ts`) и обновить эту страницу: строка в разделе 3, подробности в разделе 4.
